# RepoMatch

**Find the open-source project that actually fits your skills — and the exact issue to fix first.**

RepoMatch takes a short developer profile (skills, interests, experience) and
returns five live GitHub repositories that are actively welcoming new
contributors, ranked by fit, each paired with a real `good first issue` you
can open today.

Every repository, every issue title, and every issue link comes from the real
GitHub API. The reasoning behind each match is generated by **Gemma running
locally** through Ollama. No cloud LLM, no database, no scraped dataset.

Live demo: **https://repomatch-pied.vercel.app**

---

## What makes it different

Most "find a project" tools return a list of popular repos and leave you to
figure out where to start. RepoMatch returns a **specific, verified issue**:

- Every suggestion has an open `good first issue` — nothing to hunt for
- Issue **title and URL always come from GitHub**, never from the model. The
  model chooses *which* issue; GitHub provides its text and link, so a
  hallucinated issue number can't produce a broken link
- Matches are ranked by a deterministic pre-filter *before* the AI runs, so
  the model never wastes time on an unreachable repo
- Models routinely produce reasoning or malformed JSON. All of it is stripped,
  clamped and validated before anything reaches you

## How it works

```
  profile (skills, interests, experience)
      |
      v
  [1] validate            -> 400 INVALID_PROFILE on bad input
      |
      v
  [2] cache lookup        10-minute in-memory cache, keyed by normalised profile
      |
      v
  [3] checkGemma()        -> 503 GEMMA_UNAVAILABLE if Ollama/model is down (~100 ms)
      |
      v
  [4] GitHub search       3 parallel /search calls, merged + deduped, <=15 repos
      |                   -> relaxed retry if the strict query matched nothing
      v
  [5] good-first issues   fetched for the top candidates only
      |                   -> 503 GITHUB_* on failure (never returns unverifiable repos)
      v
  [6] deterministic pre-filter -> top 5, scored by an explicit 0-100 rubric
      |
      v
  [7] Gemma analysis      one /api/chat call at a time, 90 s timeout each
      |                   -> clamp score, verify issue against real data
      v
  [8] drop repos with no good-first issue, merge, sort by matchScore desc
      |
      v
  { repositories: [...], meta: { dataSource, aiSource, cached } }
```

**The pre-filter rubric** (`backend/services/matchingService.js`):

| Signal | Weight |
| --- | --- |
| Skill / language match | 30 |
| Topic / interest match | 25 |
| Has open good-first issues | 20 |
| Recent activity | 10 |
| Star count (tiered by experience) | 15 |

### Why one topic per search query

GitHub **ANDs** repeated `topic:` qualifiers, which silently returns almost
nothing. Verified against the live API:

```
language:JavaScript topic:artificial-intelligence topic:web good-first-issues:>0  ->  0 results
language:JavaScript good-first-issues:>0                                          ->  643 results
topic:web good-first-issues:>0                                                    ->  89 results
```

So each search targets **one** language or **one** topic, and the results are
unioned at merge time. This one detail is the difference between a working
search and an empty one.

## Running it locally

### 1. Prerequisites

- **Node 18+**
- **[Ollama](https://ollama.com)** with the model installed:

```sh
ollama pull gemma4:e2b     # ~3.5 GB
```

### 2. Backend

```sh
cd backend
cp .env.example .env       # optional: add GITHUB_TOKEN (see below)
npm install
npm run dev                # http://localhost:3000
```

Check it:

```sh
curl http://localhost:3000/api/health
# {"status":"ok","gemma":true,"ollama":true,"model":"gemma4:e2b"}
```

`gemma: false` means Ollama isn't running or the model isn't installed.

### 3. Frontend

```sh
npm install
npm run dev                # http://localhost:5173
```

The frontend reads `VITE_API_URL` and defaults to `http://localhost:3000`, so
no `.env` is needed for local work.

### 4. GitHub token (strongly recommended)

Without a token, GitHub allows only **10 search requests/minute** and 60
requests/hour total; `/api/matches` needs about 13. You'll hit `503
GITHUB_RATE_LIMIT` quickly.

```sh
# https://github.com/settings/personal-access-tokens
# Public repository read access is enough.
echo 'GITHUB_TOKEN=github_pat_...' >> backend/.env
```

With a token you get 5000 requests/hour and 30 searches/minute. The startup
banner prints `GITHUB_TOKEN : set` when it took effect.

> `backend/.env` is gitignored. **Never commit a token.**

## API

### `GET /api/health`

```json
{ "status": "ok", "gemma": true, "ollama": true, "model": "gemma4:e2b" }
```

### `POST /api/matches`

```json
{ "skills": ["React", "TypeScript"], "interests": ["Developer Tools"], "experience": "beginner" }
```

```json
{
  "repositories": [
    {
      "id": 123456,
      "fullName": "owner/repo",
      "description": "...",
      "url": "https://github.com/owner/repo",
      "stars": 1200,
      "language": "TypeScript",
      "topics": ["react", "cli"],
      "goodFirstIssueCount": 4,
      "matchScore": 87,
      "whyMatch": ["Your React skill matches this project's stack", "..."],
      "summary": "A well-maintained CLI with an active contributor community.",
      "recommendedIssue": {
        "title": "Improve error message for missing config file",
        "number": 731,
        "url": "https://github.com/owner/repo/issues/731",
        "difficulty": "Beginner",
        "skills": ["TypeScript"]
      }
    }
  ],
  "meta": { "dataSource": "github", "aiSource": "gemma", "cached": false }
}
```

Results are sorted by `matchScore` descending.

### Errors

Always `{ "error": string, "code": string, "message": string }`:

| Status | Code | Meaning |
| --- | --- | --- |
| 400 | `INVALID_PROFILE` | `skills` missing/empty, or bad `experience` |
| 400 | `INVALID_JSON` | body is not parseable JSON |
| 404 | `NOT_FOUND` | unknown `/api/*` path |
| 503 | `GEMMA_UNAVAILABLE` | Ollama down, or `gemma4:e2b` not installed |
| 503 | `GITHUB_RATE_LIMIT` | GitHub quota exhausted |
| 503 | `GITHUB_UNAVAILABLE` | GitHub unreachable or erroring |
| 500 | `INTERNAL_ERROR` | anything unexpected |

**There is no mock/demo data.** If GitHub can't be reached, RepoMatch returns
an actionable error instead of inventing repositories.

## Live data only

This is the project's core rule. An earlier version silently fell back to a
hardcoded dataset when GitHub failed, which showed fabricated repositories and
issues to the user as if they were real recommendations.

Now:

- `meta.dataSource` is **always** `"github"`
- GitHub failures return `503` with a message naming the actual fix
- If the strict search matches nothing, a **relaxed** retry widens the
  qualifiers (drops the star floor and topic pins, 12-month activity window)
  but still requires `good-first-issues:>0`, so narrow profiles still get
  real repositories instead of an empty deck

The only thing that can degrade is the *scoring*, and only when Ollama is up
but a single call misbehaves — in which case `aiSource` is `"fallback"` and
the deterministic rubric is used. The repository data is still real.

## Deployment

The frontend is deployed to Vercel. **The backend and all AI run locally**,
because Vercel's serverless functions cannot reach `localhost:11434`:

```
browser ──> Vercel (static React)
        ──> ngrok tunnel
        ──> localhost:3000 (Express)
        ──> localhost:11434 (Ollama + gemma4:e2b)
```

`VITE_API_URL` is stored as a Vercel env var rather than committed, because
ngrok free URLs change on every restart.

> **Consequence:** the site loads anywhere, but searches only work while the
> machine running Ollama is awake. To make it fully independent you'd need to
> host the model, which trades away the "no cloud LLM" property.

### Vercel env vars

| Name | Public? | Purpose |
| --- | --- | --- |
| `VITE_API_URL` | **yes** — compiled into the JS bundle | backend origin the browser calls |
| `GITHUB_TOKEN` | no — server-side only | not read by Vercel; the local backend uses `backend/.env` |

Only `VITE_`-prefixed variables are inlined into the browser bundle. Never
prefix a secret with `VITE_`.

Expect `meta.dataSource` to be `"github"` and every returned issue URL to
resolve to a real open GitHub issue.

## Notes and limits

- **First search takes 15–90 s.** Five sequential Gemma inferences plus live
  GitHub calls. Repeat searches on an identical profile return instantly from
  the 10-minute cache.
- **Sequential by design.** Gemma calls run one at a time to avoid
  overwhelming a local GPU; this is the main latency cost.
- **Model output is never trusted.** Scores are clamped to 0–100, `whyMatch`
  is coerced to a string array, and the recommended issue number is verified
  against the real issue list before use.
- **Anonymous GitHub access is tight** (10 searches/min). Use a token.
